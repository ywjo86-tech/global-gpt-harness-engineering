## LOSSLESS SOURCE PROJECTION — EXECUTIVE SUMMARY / APPROVED SCOPE / CONSTRAINTS
# ID-01 Executive Summary

## Purpose

PHASE 3 — Execution Backend Contract Finalization의 승인된 WHAT을 실제 구현 가능한 HOW로 고정한다. 핵심은 현재 Full Plan Codex Worker 경로의 legacy launcher를 실제 설치 Codex CLI가 제공하는 비대화형 인터페이스에 맞추고, 이 호환성 판단을 실행 전 Preflight와 실제 Worker smoke 및 폐쇄적 Entry Gate로 강제하는 것이다.

## Design Goal

CLI-specific 변화는 `Execution Backend Adapter → Launcher Contract → Actual Installed Runtime/CLI` 경계 내부에서 흡수한다. Orchestrator, Provider Router authority, Result Normalization, Fan-in, Stage Gate, Completion/Worker Authority의 의미는 보존한다. Runtime capability를 실행 시점에 검출해 지원 가능한 launcher contract만 선택하고, unknown/unsupported 상태는 `BACKEND_LAUNCHER_COMPATIBILITY_FAILED`로 fail-closed 처리한다.

## Expected Implementation Outcome

1. 현재 설치 Runtime에서 `codex exec` 기반 launcher contract가 실제 Worker 단위로 동작한다.
2. prompt는 stdin transport를 사용하고, 결과는 Codex final structured output을 Adapter가 canonical Worker Result v1로 normalize한다.
3. unsupported/deprecated subcommand/option, PATH/executable 문제, prompt/result transport mismatch, abnormal-success ambiguity가 Gate 이전에 차단된다.
4. read-only backend diagnostic, isolated state-changing, execution failure/manual fallback, Provider Separation 실제 smoke가 각각 독립 증거를 만든다.
5. state-changing capability가 `read_only`보다 우선하며 `filesystem_write`, `shell`, `test`, `git`, `implementation`, `integration`은 NVIDIA 실행 대상이 될 수 없다.
6. Codex→manual fallback은 유지되고 NVIDIA→Codex automatic fallback은 존재하지 않는다.
7. Graphify PHASE 2와 Full Plan 핵심 regression이 모두 PASS하고 최종 evidence package가 완결될 때만 PHASE 3 Entry Gate가 GO가 된다.

# EC-03 ARCHITECTURE / COMPONENTS / CHANGE TARGETS

## LOSSLESS SOURCE PROJECTION — ARCHITECTURE / COMPONENTS / CHANGE TARGETS
# ID-06 Architecture Design

## Current Architecture Boundary

Current backend-specific boundary begins at the Provider Executor's Codex branch and ends when a canonical Worker Result is written. Current CLI command construction is embedded in `codex_adapter.py`, while upper layers depend only on provider decision and result artifacts.

## Target Architecture

```text
Orchestrator / Task Package
  → Provider Router (authority preserved)
  → Provider Executor
  → Codex Adapter
      → Codex Launcher Capability Probe
      → Launcher Contract Resolver
      → Codex Process Executor
      → Structured Final Output Decoder
      → Worker Result Normalizer
  → Result Collector
  → Fan-in
  → Stage Gate
```

PHASE 3 readiness is a separate verification plane:

```text
Current Source Verification
  → Execution Backend Preflight
  → Launcher Contract Verification
  → Live Smoke A/B/C/D
  → Core/Graphify Regression
  → Evidence Package
  → PHASE 3 Entry Gate Evaluator
```

## Preserved Architecture

- Orchestrator and Planner remain provider-neutral.
- Provider Router remains sole provider-selection authority.
- Worker Result schema `orchestration.worker.result.v1` remains canonical downstream contract.
- Result Collector, Fan-in, Stage Gate, Completion/Worker Authority semantics remain unchanged.
- manual fallback remains the Codex execution recovery path.
- NVIDIA failure does not reroute automatically to Codex.
- separate Codex App Server dynamic-tool transport/readiness remains separate and pinned according to its own existing contract.

## Changed Architecture

- move CLI-specific command selection from static legacy `_build_command` to a dedicated current-runtime capability/contract resolver.
- add explicit process timeout/cancellation handling.
- formalize prompt/cwd/sandbox/result transport for `codex exec`.
- validate `CODEX_CLI_COMMAND` overrides rather than trusting them.
- add fail-closed compatibility taxonomy and Preflight record.
- correct state-changing capability precedence for `implementation` and `integration` without changing Provider Router authority.
- add PHASE 3 backend Entry Gate evaluator and evidence schema.

## New Architecture Elements

- `codex_launcher.py`: current-runtime probe, supported-contract resolution, invocation execution, bounded process result.
- `execution_backend_preflight.py`: preflight collection and compatibility status.
- `execution_backend_entry_gate.py`: pure conjunctive gate evaluation and final evidence validation.
- `docs/harness/execution-backend-contract.md`: documented Launcher Contract + Known Issue lifecycle.
- PHASE 3 smoke/evidence tests and isolated fixture runtime.

## Component Details

### CMP-101 — Codex Launcher Contract
Responsibility: Inspect the actual installed CLI and produce a bounded launcher manifest plus a resolved invocation specification only when required capabilities are present.  
Inputs: executable lookup, CLI help/version output, project root, output directory, required capabilities, optional existing `CODEX_CLI_COMMAND`.  
Outputs: `CodexCliCapabilityManifest`, `CodexLauncherInvocation`, or compatibility failure taxonomy.  
Dependencies: Python stdlib only.  
State Behavior: stateless; manifest can be serialized as evidence.  
Error Behavior: any missing/ambiguous required capability yields `BACKEND_LAUNCHER_COMPATIBILITY_FAILED`.  
Compatibility Considerations: version is recorded but not used as sole allow/deny key.  
Preserved Behavior: no upper-layer CLI string knowledge.

### CMP-102 — Codex Process Executor
Responsibility: Execute the resolved invocation with stdin prompt and bounded process policy.  
Inputs: invocation, prompt text, timeout.  
Outputs: return code, stdout, stderr, duration, timeout/cancel status, final-message path existence.  
Dependencies: `subprocess.Popen`.  
State Behavior: child process only.  
Error Behavior: timeout → terminate → 5-second grace → kill; no automatic retry.  
Compatibility Considerations: no shell string execution; argv list only.  
Preserved Behavior: caller decides manual fallback.

### CMP-103 — Codex Adapter
Responsibility: preserve public task execution behavior while replacing legacy command build with CMP-101/CMP-102.  
Inputs: prompt path, output directory, execution mode, optional project root and required capabilities.  
Outputs: completed result metadata or existing manual fallback artifact/status.  
Dependencies: CMP-101/102, CMP-110.  
State Behavior: writes launcher log, structured final response, canonical result/handoff artifacts in task output dir.  
Error Behavior: bounded compatibility/runtime errors become `manual_fallback` with taxonomy.  
Compatibility Considerations: existing positional parameters remain valid; new context is keyword-only with safe defaults.  
Preserved Behavior: `mock`, `manual`, CLI missing/failure fallback semantics.

### CMP-104 — Provider Router
Responsibility: preserve Provider Router authority and approved HYBRID split.  
Inputs: mode + required capabilities.  
Outputs: provider decision.  
Dependencies: execution mode vocabulary only.  
State Behavior: pure deterministic function.  
Error Behavior: unsafe/contradictory capability cannot become NVIDIA-eligible.  
Compatibility Considerations: only adds approved state-changing capability vocabulary `implementation`, `integration`; no provider/routing expansion.  
Preserved Behavior: normal read-only/reasoning eligible path; existing non-read-only path; no NVIDIA→Codex failure fallback logic is introduced.

### CMP-108 — Execution Backend Preflight
Responsibility: produce the pre-implementation runtime compatibility baseline.  
Inputs: repository identity/baseline, CMP-101 manifest, process policy, known issue metadata, focused static checks.  
Outputs: `execution_backend_preflight.json` with status `PASS` or `BACKEND_LAUNCHER_COMPATIBILITY_FAILED`.  
Dependencies: current source and actual CLI.  
State Behavior: evidence-only; no product/core mutation.  
Error Behavior: any unknown is failure.  
Compatibility Considerations: current version and invocation shape are evidence, not permanent source constants.  
Preserved Behavior: untracked historical runtime artifacts are not deleted/promoted.

### CMP-109 — Execution Backend Entry Gate
Responsibility: evaluate the exact approved final conjunction and 10-question result.  
Inputs: preflight, four smoke records, fallback/routing/core regression/Graphify regression records, changed-file/core-change record, Known Issue closure, 10-question matrix.  
Outputs: final gate record with `GO` or `NO_GO`.  
Dependencies: evidence only.  
State Behavior: pure evaluator + serialized decision record.  
Error Behavior: missing/unknown/CONDITIONAL data → `NO_GO`.  
Compatibility Considerations: gate does not execute providers or mutate router.  
Preserved Behavior: approved mandatory conjunction.

## Interface Details

### IF-101 — `probe_codex_cli_capabilities()`
Input: no provider-selection input; optional executable resolver for testing.  
Output fields:
- `executable_detected: bool`
- `executable_path_fingerprint: str` (hash, not required to expose full path in packaged evidence)
- `cli_version: str`
- `exec_subcommand: bool`
- `stdin_prompt: bool`
- `cwd_option: bool`
- `sandbox_option: bool`
- `output_schema_option: bool`
- `output_last_message_option: bool`
- `json_events_option: bool`
- `probe_returncodes`
- `status`

Contract: required booleans except `json_events_option` must be true to resolve the default launcher contract.  
Error Handling: executable missing, help invocation failure, unparseable/ambiguous required capability → compatibility failure.  
Compatibility: no equality check against `0.150.1` for the Worker launcher.  
Security: raw environment/secrets are not serialized.

### IF-102 — `resolve_codex_launcher(...)`
Input: capability manifest, project root, output dir, required capabilities, optional override.  
Output: argv list, stdin mode, sandbox mode, output schema path, final output path, optional JSON events flag.  
Contract: default current invocation shape is logically equivalent to:
`codex exec -C <project_root> --sandbox <read-only|workspace-write> --output-schema <schema> -o <final-output> [--json] -`
The exact executable path and optional flag presence come from capability resolution.  
Error Handling: any legacy/unsupported override or required option omission fails closed.  
Compatibility: prompt content is not embedded in argv.  
Security: never emit `--dangerously-bypass-approvals-and-sandbox` or `--dangerously-bypass-hook-trust`.

### IF-103 — `execute_codex_invocation(...)`
Input: argv + prompt text + timeout 600s.  
Output: process result record.  
Contract: retry=0; timeout→terminate→5s grace→kill.  
Error Handling taxonomy includes `CLI_NOT_FOUND`, `COMPATIBILITY_FAILED`, `TIMEOUT`, `CANCELLED`, `NONZERO_EXIT`, `STRUCTURED_OUTPUT_MISSING`, `STRUCTURED_OUTPUT_INVALID`, `ABNORMAL_SUCCESS_AMBIGUITY`.  
Compatibility: `returncode=0` is necessary but not sufficient for success.  
Security: shell=False.

### IF-104 — Adapter Entry
Input: existing three positional args plus optional keyword `project_root`, `required_capabilities`.  
Output: same high-level completed/manual fallback contract plus optional bounded `backend_failure_class` / launcher evidence reference.  
Contract: callsites never build CLI argv.  
Error Handling: compatibility/runtime errors preserve manual fallback.  
Compatibility: existing callers remain source-compatible.  
Security: sandbox mode derives from capabilities, not provider labels.

### IF-105 — Structured Final Output
The launcher generates a bounded JSON Schema in the task output directory. Minimum accepted final fields are:
- `thread_id`
- `agent_name`
- `status`
- `summary`
- `findings[]`
- `warnings[]`
- `errors[]`
- `artifacts[]`
- `next_step`

Adapter parses the `-o` file as JSON, passes it through `normalize_worker_result`, writes canonical `result.json`, then renders `handoff_report.md` and `worker_handoff.md`. Missing/invalid structured final output is not treated as success even if exit code is zero.

### IF-106 — Provider Route
`STATE_CHANGING_CAPABILITIES = {filesystem_write, shell, test, git, implementation, integration}`.  
If any state-changing capability exists, `read_only` cannot make the task NVIDIA-eligible.  
No Provider assignment is introduced into planning/task ownership.

### IF-108 — Preflight Record
Canonical top-level fields:
- identity/baseline binding
- `cli`
- `launcher_contract`
- `process_policy`
- `fallback_policy`
- `result_flow_contract`
- `known_issue`
- `compatibility_status`
- `blocking_reasons[]`
- evidence references

### IF-109 — Entry Gate
All approved mandatory predicates plus Graphify regression and Provider Separation smoke must be true. 10/10 final questions must be YES. Missing evidence is false. Output is `GO` or `NO_GO`; final `CONDITIONAL_GO` is not accepted.

# ID-09 Data / Control / State Flow

## Data Flow

1. `TaskSlice` provides prompt path, output dir, project root context and provider-neutral `required_capabilities`.
2. Provider Router decides the execution backend from approved HYBRID policy.
3. Codex Adapter requests a current capability manifest from Launcher Contract.
4. Launcher Contract resolves an argv specification only if required capabilities are verified.
5. Adapter reads prompt text and sends it through stdin.
6. CLI runs with explicit project cwd and capability-derived sandbox.
7. CLI writes only its structured final response to `-o` path; optional JSONL events remain diagnostic stdout.
8. Adapter validates return code + structured output presence/schema + expected task binding.
9. Adapter normalizes payload into existing Worker Result v1 and writes canonical result/handoff artifacts.
10. existing Collector → Fan-in → Stage Gate consume the same canonical result format as before.

## Control Flow

1. Execution-time Preflight checks source binding and actual CLI capabilities.
2. Compatibility unknown/fail closes Entry Gate before normal PHASE 3 use.
3. During a Codex task, Adapter re-probes or consumes a same-run fresh capability record; stale/mismatched manifest fails closed.
4. Valid contract executes once; there is no automatic CLI retry.
5. CLI runtime/contract failure becomes existing manual fallback plus explicit failure taxonomy.
6. Runtime smoke tests validate direct backend diagnostic, isolated action, fallback and Provider Separation independently.
7. Regression and evidence closure feed final Entry Gate.

## State Transitions

| Current State | Event | Next State | Failure State |
|---|---|---|---|
| `UNVERIFIED` | capability probe complete | `COMPATIBILITY_VERIFIED` | `BACKEND_LAUNCHER_COMPATIBILITY_FAILED` |
| `COMPATIBILITY_VERIFIED` | invocation resolved | `LAUNCH_READY` | `BACKEND_LAUNCHER_COMPATIBILITY_FAILED` |
| `LAUNCH_READY` | CLI execution succeeds + structured result valid | `WORKER_RESULT_READY` | `MANUAL_FALLBACK_REQUIRED` |
| `WORKER_RESULT_READY` | normalization succeeds | `NORMALIZED` | `MANUAL_FALLBACK_REQUIRED` |
| `NORMALIZED` | collection/fan-in/gate convergence validated | `SMOKE_PASS` | `REMEDIATION_REQUIRED` |
| `SMOKE_PASS` | regressions + evidence complete | `ENTRY_GATE_EVALUATION` | `REMEDIATION_REQUIRED` |
| `ENTRY_GATE_EVALUATION` | all mandatory predicates + 10/10 YES | `GO` | `NO_GO` |

Manual fallback is not a state upgrade from compatibility failure; it is recovery evidence only.
