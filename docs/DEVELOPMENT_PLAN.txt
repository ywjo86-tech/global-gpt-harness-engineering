# EC-01 SCOPE

## ID-01 Executive Summary
### Purpose
승인된 `GH-FULL-MCP-PH4_APPROVED_DEVELOPMENT_PLAN.md`의 PHASE 4 WHAT을 실제 구현 가능한 HOW로 고정한다. Full MCP는 기존 Execution Backend Contract 뒤에서 동작하는 교체 가능한 로컬 Execution Runtime이며 Filesystem, Shell, Git, Test/Build/Lint, Status/Validate, Audit/Failure/Recovery/Restore를 통제된 MCP tool surface로 제공한다.

### Design Goal
기존 Provider Router, HostExecutionGateway, ToolAuthorizationContract, ToolEffectJournal, Project Isolation, Result/Recovery primitives를 보존·재사용하고 `runtime/full_mcp/`에 독립 런타임을 추가한다. Consumer/Core는 Full MCP 내부 모듈이나 MCP SDK를 직접 import하지 않고 기존 Execution Backend Contract만 소비한다.

### Expected Implementation Outcome
Python 3.12 + MCP Python SDK 2.2.0 + MCP 2026-07-28 + stdio 기반 Full MCP Runtime이 isolated UPGRADE-003 worktree에서 구현·검증된다. 모든 PHASE 4 공식 Exit Gate가 PASS한 경우에만 `MCP_STABLE_BASELINE` 선언 패키지가 준비되며, 실제 선언/실행/병합/배포는 이후 승인 프로젝트 권한에 따른다.

# EC-03 ARCHITECTURE / COMPONENTS / CHANGE TARGETS

## ID-06 Architecture Design

### Current Architecture Boundary
The current stable execution path already has Provider routing, a validated HostExecutionGateway, per-operation authorization primitives, effect journaling, project isolation, result collection and recovery primitives. The Full MCP design does not replace these authorities. It adds one execution-runtime implementation behind the existing contract.

### Target Architecture
```text
Core / Future Consumer
        |
        v
EXECUTION_BACKEND_CONTRACT_FINAL          [PRESERVE]
        |
        v
HostExecutionGateway / authenticated UDS  [PRESERVE WIRE]
        |
        v
FullMCPBackendAdapter                     [NEW]
        |
        v
MCP Client (mode="2026-07-28")
        | stdio only
        v
Full MCP Low-Level Server                  [NEW]
        |
        v
Invocation/Auth Context + Closed Registry
        |
  +-----+---------+-----------+-------------+
  |               |           |             |
Filesystem     Process       Git        Validation
  |               |           |             |
  +---------------+-----+-----+-------------+
                        |
               Observability / Effect Journal
                        |
                Recovery / Restore Boundary
```

### Preserved Architecture
- Provider Router and HYBRID provider eligibility semantics.
- Execution Backend Contract request/result meaning.
- HostExecutionGateway authenticated UDS request/result validation.
- Existing ToolAuthorizationContract and ToolEffectJournal generic semantics.
- Existing sealed UPGRADE-002 history/source.

### Changed Architecture
- Host runner gains an implementation-neutral `ExecutionRuntimeHandler` hook; its validated wire request/result schema is unchanged.
- A dedicated Full MCP adapter becomes one runtime handler implementation.

### New Architecture Elements
- `runtime/full_mcp/` package.
- MCP 2026-07-28 stdio server/tool catalog.
- Sealed invocation context, path policy, validation profiles and structured Full MCP observability.
- Dedicated dependency manifest and Full MCP test suite.

### Component Details

#### CMP-003 — Full MCP Backend Adapter
Responsibility: receive an already validated gateway request and execute the corresponding Full MCP operation sequence through the MCP client.
Inputs: gateway request, invocation context, active authorization contracts, owned/read scopes, sealed validation profiles.
Outputs: existing gateway-compatible result plus bounded Full MCP structured result/evidence references.
Dependencies: CMP-004; preserved IF-001 Execution Backend Contract request/result boundary; IF-021 abstract `ExecutionRuntimeHandler` hook. CMP-003 has no dependency on the concrete CMP-014 component.
State Behavior: one adapter invocation owns one stdio MCP child lifecycle; no cross-request hidden session state. The adapter transfers canonical InvocationContext once through an anonymous inherited read-only pipe FD; environment contains only the FD number and context digest, never authorization payloads.
Error Behavior: applies the exact ID-08 Full MCP error → gateway failure mapping; never converts failure into success.
Compatibility Considerations: consumer contract and gateway request/result wire fields remain unchanged.
Preserved Behavior: Provider selection/fallback occurs before this component.

#### CMP-004 — Full MCP stdio Server
Responsibility: expose tools only; no resources/prompts, UI, planning, workflow or provider routing.
Inputs: MCP `tools/list` and `tools/call` over stdio; request `_meta` invocation binding.
Outputs: structured tool results and application `_meta` correlation fields.
Dependencies: official MCP SDK 2.2.0, CMP-005, CMP-006.
State Behavior: request-bound; durable state lives only in explicit effect/observability stores.
Error Behavior: unknown tool/schema/auth mismatch returns bounded error and no operation dispatch.
Compatibility Considerations: client pins 2026-07-28; custom `gch/full-mcp/*` metadata is additive to SDK-managed protocol/client metadata and never replaces it.
Preserved Behavior: no network listener.

#### CMP-005 — Full MCP Runtime/Broker
Responsibility: be the sole server-side dispatch authority from a validated MCP tool call to a registered operation implementation.
Inputs: validated tool name/arguments, in-memory InvocationContext, exact active ToolAuthorizationContract, closed RegisteredOperation definition.
Outputs: Common Full MCP Tool Result or a closed error result; state-changing operations additionally produce effect intent/receipt identity.
Dependencies: CMP-006~CMP-013 and preserved CMP-015.
State Behavior: registry is sealed before the MCP loop; unknown/duplicate operation registration is fatal at startup. For a state-changing call the broker authorizes first, writes create-once effect intent second, invokes the service once, then seals receipt/result. Read-only calls never create mutation receipts.
Error Behavior: auth/policy/schema failure blocks before service dispatch; intent-without-trusted-receipt becomes `RECOVERY_REQUIRED`; broker never auto-replays an ambiguous state-changing request.
Compatibility Considerations: operation names and schemas are internal to Full MCP and are translated by CMP-003; no consumer depends on the registry class or tool names.
Preserved Behavior: ToolAuthorizationContract exact-match semantics and ToolEffectJournal create-once semantics remain unchanged.

#### CMP-006 — Invocation/Auth Context
Responsibility: authenticate/bind downstream MCP calls to the already authenticated gateway request.
Inputs: gateway request digest, project/run/gate/LV/attempt identity, active tool authorization contracts, scope digests, validation-profile digests.
Outputs: immutable `invocation_context_id` and operation identity material.
Dependencies: existing `validate_gateway_request`, ToolAuthorizationContract validation.
State Behavior: created once per adapter invocation, serialized as canonical JSON into an anonymous pipe, read exactly once by the child before the MCP loop, verified against the adapter-supplied SHA-256 digest, then held in memory/server lifespan. No context file or authorization payload is persisted or placed in argv/stdin/stdout.
Error Behavior: missing/mismatched `_meta` binding blocks before broker dispatch.
Compatibility Considerations: no OAuth/HTTP auth is introduced because PHASE 4 transport is local stdio behind authenticated UDS.
Preserved Behavior: UDS peer credential/auth boundary remains authoritative upstream.

#### CMP-007 — Workspace Path Policy
Responsibility: normalize and authorize all workspace paths.
Inputs: execution workspace root, read scopes, mutable owned scopes, relative target.
Outputs: canonical safe path or closed policy error.
Dependencies: InvocationContext scope bindings.
State Behavior: none.
Error Behavior: absolute outside-root, `..`, symlink traversal, `.git`, `.env`, credential/token-like sensitive path classes are blocked unless an explicitly approved read-only exception exists; `.git` mutation is prohibited outside Git service internals.
Compatibility Considerations: all service paths pass through this component.
Preserved Behavior: canonical TARGET_PROJECT_ROOT identity remains unchanged; an isolated execution worktree is an execution workspace, not a new project root.

#### CMP-008 — Filesystem Service
Responsibility: REQ-002~REQ-006.
Inputs: exact IF-005~IF-009 schemas.
Outputs: exact bounded data payloads defined in ID-08; raw content is transient and security-scanned before return.
State Behavior: writes are temp-file + fsync + atomic replace; patch is base-hash-bound and all-or-nothing.
Error Behavior: size/encoding/path/policy/conflict errors use the closed taxonomy.
Compatibility Considerations: no shell command is required for filesystem operations.
Preserved Behavior: outside-root mutation is blocked.

#### CMP-009 — Process Service
Responsibility: REQ-007~REQ-009 and SEC-003.
Inputs: exact IF-010 schema.
Outputs: exit code, stdout, stderr, timeout/cancel status and output digests.
State Behavior: new process group; timeout/cancel sends TERM then bounded KILL; detached children are prohibited.
Error Behavior: spawn/nonzero/timeout/cancel/output-limit are distinct.
Compatibility Considerations: `shell=False`; `bash -c`/`sh -c` rejected by default ShellPolicy.
Preserved Behavior: no network/package install unless separately authorized execution task.

#### CMP-010 — Git Service
Responsibility: REQ-010~REQ-014.
Inputs: exact IF-011~IF-015 schemas plus approved workspace/ref/path scopes.
Outputs: structured status/diff/branch/restore/commit-preparation data.
State Behavior: restore is the only source-tree mutation and is effect-journaled. Commit preparation is read-only and does not stage/commit.
Error Behavior: remote/network/destructive/unsupported operations fail closed.
Compatibility Considerations: no push/deployment authority.
Preserved Behavior: sealed baseline and main isolation.

#### CMP-011 — Validation Service
Responsibility: REQ-015~REQ-020.
Inputs: sealed `profile_id` or exact validate expectations, never raw unsealed validation command from MCP tool arguments.
Outputs: bounded command result/status/validation verdict.
State Behavior: profile catalog is canonicalized and digest-bound into InvocationContext; only ID-13 catalog entries are executable.
Error Behavior: unknown/mismatched profile, spawn/nonzero/timeout are distinct; no silent skip.
Compatibility Considerations: command mapping is fixed by the approved source Implementation Design and may change only through its approved revision path.
Preserved Behavior: Full MCP owns execution only, not test strategy planning.

#### CMP-012 — Observability Store
Responsibility: OPS-001~OPS-003, OPS-009 and NFR-004.
Inputs: lifecycle event objects.
Outputs: append-only JSONL events plus result/evidence indexes under `_workspace/full-mcp/<run_id>/`.
State Behavior: UTC timestamps, monotonically ordered request event sequence, correlation IDs and digests.
Error Behavior: persistence failure blocks completion evidence; it never downgrades to untracked success.
Compatibility Considerations: schema is product/backend-neutral; no dashboard contract.
Preserved Behavior: raw file content, raw stdout/stderr, auth material and Full MCP class names are not durable fields.

#### CMP-013 — Recovery Coordinator
Responsibility: OPS-004~OPS-005 with explicit invalidation propagation.
Inputs: terminal error, effect journal state, changed Change Target IDs/paths, current Test source-closure matrix, selected ValidationResult/Evidence/Gate references, baseline/ref and allowed restore scope.
Outputs: recovery classification, affected Test IDs, stale Evidence IDs, invalidated Gate IDs, earliest invalidated prerequisite gate and required remediation/validation sequence.
Dependencies: immutable primitive policy in `runtime/full_mcp/recovery.py`; pre-GATE-002 integrated orchestration in `runtime/full_mcp/recovery_integration.py` created by TASK-011 and reused by later gate recovery; CMP-010, CMP-012, CMP-020.
State Behavior: primitive recovery rules are created once by TASK-008 and never modified later. TASK-011 adds integration in a separate module. Remediation impact is computed by changed CT/path → Test source set → ValidationResult freshness → Evidence eligibility → Gate dependency graph. Historical records remain immutable; only eligibility becomes STALE.
Error Behavior: ambiguous effect blocks auto-rerun. If remediation invalidates a prerequisite GO gate, recovery starts at the earliest invalidated prerequisite, re-establishes gates in order, and then returns to the originally failed gate. The failed gate is never bypassed.
Compatibility Considerations: preserves the required Failure → Diagnose → Remediate → Focused Validation → Regression → Independent Review → Same Gate Re-evaluation sequence while allowing prerequisite restoration before the same failed gate is retried.
Preserved Behavior: no reset/clean fallback; no silent replay; no rewrite of historical Evidence/Gate records.

#### CMP-014 — Host Execution Gateway

Dependencies: preserved request/result validators, authenticated UnixSocketGatewayTransport and DurableExecutionLedger; IF-021 abstract runtime-handler hook/configuration only. CMP-014 has no dependency on the concrete CMP-003 component.
State Behavior: request identity/digest, peer UID/socket permission and create-once ledger semantics remain upstream of Full MCP. Runtime handler selection is configuration-bound, not provider selection.
Error Behavior: malformed transport/request/result remains `GatewayError`; Full MCP outcomes are projected through the exact ID-08 mapping into existing `execution_status`, `process_termination_category` and `exit_status_category` fields.
Compatibility Considerations: `gateway_contract_version`, request/result required-field sets and digest algorithm are unchanged.
Preserved Behavior: existing gateway authentication, duplicate-request prevention, result validation and ledger transitions.

### Interface Details

#### Common Full MCP Tool Input Envelope
Every tool call carries the following application keys in MCP `_meta`:
- `gch/full-mcp/invocation_context_id: string`
- `gch/full-mcp/request_digest: 64-lowercase-hex`
- `gch/full-mcp/correlation_id: string`
- `gch/full-mcp/operation_request_id: string`

These keys are **additive** to MCP/SDK-managed protocol-version, client-identity and capability metadata required by the 2026-07-28 protocol. Application code must not overwrite SDK-managed reserved metadata. Tool arguments contain operation data only; authentication/authorization payloads are never model-facing tool arguments. Before any broker dispatch the server matches all four application keys to the one-shot in-memory InvocationContext.

#### Common Full MCP Tool Result
Every successful or failed tool call returns one object with:
- `schema_version = "gch.full-mcp.result.v1"`
- `operation_request_id: string`
- `correlation_id: string`
- `operation: string`
- `status = COMPLETED | BLOCKED | FAILED | CANCELLED`
- `started_at: RFC3339 UTC`, `ended_at: RFC3339 UTC`, `duration_ms: integer >= 0`
- `data: object | null` — exact per-tool payload below
- `exit_code: integer | null` — non-null only for process-backed execution
- `stdout: string | null`, `stderr: string | null` — only where the interface requires them and only after security/bounds checks
- `result_digest: 64-lowercase-hex`
- `audit_ref: workspace-relative artifact reference`
- `effect_id: string | null`
- `error: null | {code: ErrorCode, stage: string, retryable: boolean}`

Durable audit/evidence records never embed raw tool arguments, file contents, stdout/stderr, secrets or auth metadata.

#### Exact MCP Tool Schemas
All paths are POSIX workspace-relative strings after schema validation and before path-policy resolution. Unknown input fields are rejected.

| Interface | Exact arguments | Exact `data` payload on `COMPLETED` | Key constraints |
|---|---|---|---|
| IF-005 `filesystem_read` | `{path:str, encoding:"utf-8"="utf-8", max_bytes:int=1048576}` | `{path:str, size:int, sha256:str, encoding:"utf-8", text:str}` | regular file only; `1 <= max_bytes <= 1048576`; oversize fails rather than silently truncating |
| IF-006 `filesystem_write` | `{path:str, content:str, expected_absent:bool=false, expected_sha256:str\|null=null}` | `{path:str, before_sha256:str\|null, after_sha256:str, bytes_written:int}` | mutable-owned file only; optimistic precondition required for replacement; atomic write; effect-journaled |
| IF-007 `filesystem_patch` | `{path:str, base_sha256:str, edits:list[LineEdit], final_newline:bool\|null=null}` | `{path:str, before_sha256:str, after_sha256:str, changed_line_count:int}` | `LineEdit={start_line:int>=1,end_line:int>=start_line,replacement:str}`; edits ordered/non-overlapping; effect-journaled |
| IF-008 `filesystem_search` | `{root:str=".", query:str, mode:"LITERAL"\|"REGEX"="LITERAL", glob:str="**/*", max_matches:int=200, max_file_bytes:int=1048576}` | `{matches:list[{path:str,line:int,column:int,text:str}], match_count:int}` | `1 <= max_matches <= 200`; no binary/oversize file search; regex compile failure is input error |

#### ValidationProfile Contract
Canonical fields: `profile_id`, `kind = UNIT|INTEGRATION|BUILD|LINT`, `argv[]`, `cwd`, `timeout_seconds`, `env_allowlist[]`, `profile_digest`.
`cwd` is workspace-relative and resolves against `InvocationContext.workspace_root`; the catalog is sealed into InvocationContext. `profile_digest = sha256(canonical_json(profile_without_profile_digest))`. `validation_execute` accepts only `profile_id` and never accepts raw argv/cwd/env overrides.

#### Error Taxonomy
`AUTHENTICATION_FAILED`, `AUTHORIZATION_DENIED`, `INPUT_SCHEMA_INVALID`, `WORKSPACE_VIOLATION`, `PATH_POLICY_VIOLATION`, `SYMLINK_VIOLATION`, `SENSITIVE_PATH_BLOCKED`, `COMMAND_NOT_ALLOWED`, `PROCESS_SPAWN_FAILED`, `PROCESS_TIMEOUT`, `PROCESS_CANCELLED`, `NONZERO_EXIT`, `OUTPUT_LIMIT_EXCEEDED`, `SECRET_OUTPUT_BLOCKED`, `GIT_BOUNDARY_VIOLATION`, `PATCH_CONFLICT`, `VALIDATION_FAILED`, `EFFECT_REPLAY_BLOCKED`, `RECOVERY_AMBIGUOUS`, `PERSISTENCE_FAILED`, `INTERNAL_ERROR`.

#### Full MCP Error → Existing Gateway Result Mapping
The existing `HOST-GATEWAY.v1` required fields and digest algorithm do not change. CMP-003 projects internal outcomes using only currently established gateway categories `EXITED`, `EXIT_0`, `NONZERO` and existing `execution_status = COMPLETED|FAILED|BLOCKED`.

| Full MCP outcome/error | Gateway `execution_status` | `process_termination_category` | `exit_status_category` | Projection rule |
|---|---|---|---|---|
| Tool `COMPLETED` | `COMPLETED` | `EXITED` | `EXIT_0` | normal successful projection |
| `AUTHENTICATION_FAILED`, `AUTHORIZATION_DENIED`, `INPUT_SCHEMA_INVALID`, `WORKSPACE_VIOLATION`, `PATH_POLICY_VIOLATION`, `SYMLINK_VIOLATION`, `SENSITIVE_PATH_BLOCKED`, `COMMAND_NOT_ALLOWED`, `GIT_BOUNDARY_VIOLATION`, `EFFECT_REPLAY_BLOCKED`, `RECOVERY_AMBIGUOUS` | `BLOCKED` | `EXITED` | `NONZERO` | policy/governance block; never retry automatically |
| `VALIDATION_FAILED`, `NONZERO_EXIT`, `PATCH_CONFLICT`, `OUTPUT_LIMIT_EXCEEDED`, `SECRET_OUTPUT_BLOCKED` | `FAILED` | `EXITED` | `NONZERO` | executed/validated but acceptance failed |
| `PROCESS_SPAWN_FAILED`, `PROCESS_TIMEOUT`, `PROCESS_CANCELLED`, `PERSISTENCE_FAILED`, `INTERNAL_ERROR` | `FAILED` | `EXITED` | `NONZERO` | operational failure; recovery policy applies |

`structured_event_metadata`, `stderr_security_metadata`, `final_message_metadata` and `worker_result_identity` remain existing generic gateway objects. They may carry safe digests/status/reference values but may not add a required Full MCP class/module/tool field to the consumer contract.

## ID-09 Data / Control / State Flow

### Data Flow
1. Approved execution package supplies Required Capabilities, owned/read scopes, validation profiles and lifecycle binding to the existing execution contract.
2. Provider Router selects provider upstream; Full MCP receives no provider-selection decision authority.
3. HostExecutionGateway validates gateway request identity/digests/UDS peer boundary.
4. FullMCPBackendAdapter builds an immutable InvocationContext, writes its canonical form to an anonymous pipe, passes only the read FD + expected context digest to the exclusive stdio Full MCP child, and closes the parent transfer handles after one-shot load.
5. Adapter pins MCP client mode to `2026-07-28`, calls a registered tool and places invocation/correlation binding in `_meta`.
6. Server validates `_meta`, closed tool schema, active authorization contract and path/policy before effect intent.
7. Service executes the operation; state-changing effects are journaled; outputs are bounded/security-scanned.
8. Observability Store appends secret-safe event/result metadata and returns audit/result references.
9. Adapter maps the result into the existing gateway result surface. Consumer never sees Full MCP module/class/runtime identifiers as required contract fields.

### Control Flow
`RECEIVED → AUTHENTICATED → AUTHORIZED → (EFFECT_INTENT for mutation) → RUNNING → EFFECT_RECEIPT → RESULT_SEALED → VALIDATED`.
Failures terminate as `BLOCKED`, `FAILED` or `CANCELLED`; an intent without trusted receipt becomes `RECOVERY_REQUIRED` and cannot auto-rerun.

### State Transitions
| Current State | Event | Next State | Failure State |
|---|---|---|---|
| RECEIVED | gateway + invocation binding valid | AUTHENTICATED | BLOCKED |
| AUTHENTICATED | active exact authorization contract | AUTHORIZED | BLOCKED |
| AUTHORIZED | read-only operation | RUNNING | FAILED |
| AUTHORIZED | state-changing operation | EFFECT_INTENT | FAILED |
| EFFECT_INTENT | launcher starts | RUNNING | RECOVERY_REQUIRED |
| RUNNING | operation succeeds | EFFECT_RECEIPT / RESULT_SEALED | FAILED/CANCELLED |
| EFFECT_RECEIPT | output/security/audit succeeds | RESULT_SEALED | RECOVERY_REQUIRED |
| RESULT_SEALED | validation expectations pass | VALIDATED | FAILED |
| RECOVERY_REQUIRED | diagnose/remediate/restore | RESTORED_PENDING_VALIDATION | BLOCKED |
| RESTORED_PENDING_VALIDATION | focused + regression + independent review | same gate re-evaluation | BLOCKED |

# EC-06 VALIDATION

## ID-13 Validation / Test Design
### Validation Strategy
Validate the lowest useful level first, then integrated contract/security/operations and finally L4 E2E + L6 regression. Test execution occurs only during authorized Full Plan execution; this contract fixes the execution/proof contracts.

Temporal rule: a Task may consume a Test for completion only after every Task in that Test's `Related Output Tasks` has completed or is the consuming Task itself at its post-change validation point. Qualification Tests are never back-projected as completion conditions for earlier owners.

Every executed Test MUST emit an immutable `gch.full-mcp.validation-result.v1` record defined in ID-16. Evidence never asserts a bare `PASS`; it references one or more exact ValidationResult digests.

Repository re-verification found no `pyproject.toml`, pytest/ruff/flake8 configuration or current project linter, while current harness qualification repeatedly uses `python3 -m unittest ...` and full discovery `python3 -m unittest discover -s tests -p 'test_*.py' -q`. Full MCP therefore preserves those conventions, uses `compileall` for build/syntax qualification, and uses a project-local deterministic lint entrypoint rather than an unpinned external linter.

# EC-09 EVIDENCE

Runtime evidence is generated only during authorized Full Plan execution. This contract fixes exact immutable proof/result/review/index/gate schemas and ordering.

`EVIDENCE_ROOT = <InvocationContext.workspace_root>/_workspace/full-mcp/<run_id>/`

`attempt` is a run-wide monotonically increasing qualification epoch. The initial sequence uses `attempt=1`. Any remediation that invalidates a gate/evidence dependency starts `attempt=N+1`; prior records remain immutable. Historical proof may remain valid history even when it is no longer eligible for the current workspace state.

Canonical paths:
- `events/execution-events.jsonl` — run-level IF-019 append-only stream; each event carries `attempt`.

- `attempts/<attempt>/validation-results/<TEST-ID>/<consumer-task-id>.json` — immutable ValidationResultRecord for one legal Test consumer execution.
- `attempts/<attempt>/evidence/EVD-###.json` — immutable producer-owned EvidenceRecord.
- `attempts/<attempt>/indexes/GATE-###.json` — immutable gate-scoped evidence/gate selection index; one per evaluated gate/attempt.
- `attempts/<attempt>/indexes/PREFINAL.json` — immutable TASK-014 pre-final input index; never contains EVD-019/EVD-020.
- `attempts/<attempt>/reviews/GATE-###.json` — immutable independent-review/finding artifact.
- `attempts/<attempt>/gates/GATE-###.json` — immutable create-once Stage Gate decision.

#### `gch.full-mcp.workspace-state.v1` — WorkspaceStateBinding
Required fields: `schema_version`, `head_sha`, `approved_target_manifest_sha256`, `tracked_diff_sha256`, `untracked_owned_manifest_sha256`, `unauthorized_change_manifest_sha256`, `unauthorized_change_count`, `captured_at_utc`, `state_digest`.

CT-018 is a namespace marker and is never recursively expanded. VERIFY/PRESERVE targets are included only when a Test source set explicitly requires them.

# EC-12 RECOVERY

## ID-19 Recovery Design
### Global Recovery and Invalidation Algorithm
Required sequence remains: Failure → Diagnose → Remediate → Focused Validation → Regression → Independent Review → Same Gate Re-evaluation.

The same failed gate is never bypassed. If remediation changes proof dependencies of an earlier prerequisite gate, prerequisite validity must first be restored:
1. Remediation records exact changed CT IDs/paths and new attempt N+1.
2. CMP-020 maps changed files through ID-13 source sets to affected Test IDs.
3. ValidationResults whose source snapshots intersect those changes become STALE for current eligibility.
4. Evidence records referencing stale ValidationResults become ineligible; GateDecisionRecords selecting those Evidence records become invalidated.
5. Determine the earliest invalidated gate in order GATE-001→GATE-006.
6. Re-run only the affected owning Test(s), produce new ValidationResult/Evidence in attempt N+1, perform required regression and independent review, then re-evaluate gates from the earliest invalidated prerequisite through the originally failed gate in order.
7. The originally failed gate must be re-evaluated last in that recovery chain; later gates remain blocked until it is GO.

Historical ValidationResult/Evidence/Review/Gate records are never rewritten.
