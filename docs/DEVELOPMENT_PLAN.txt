### Source Projection ID-01 — Executive Summary

## Purpose
본 구현설계는 승인된 PHASE 5 개발계획을 기술적 HOW로 변환하여 AOH-001 Execution Integration, AOH-003 Observability Consumer Foundation, AOH-002 AI Office Operating Layer / Workflow & Governance Foundation, AOH-004 Integrated Qualification을 구현 가능한 구조로 정의한다. 이 문서는 설계만 수행하며 코드 수정, Worker/Test 실행, 배포, 병합, Git Push, baseline 선언을 수행하지 않는다.

## Design Goal
AI Office를 `AI Company Operating Layer + Workflow/Governance Runtime`으로 추가하되 기존 Full Plan, Multi-Provider Router, MPRF, Execution Backend Contract, Full MCP 권한을 이동시키지 않는다. AI Office는 requirement intake, office/workflow state, context assembly, system capability owner routing, agent/capability governance, Foundry, approval/risk/activation governance, recovery coordination, observability consumption, office-level reporting을 소유한다. 상태 변경은 오직 승인된 Execution Backend/Full MCP 또는 기존 bounded Manual Action 경로로 위임한다.

## Expected Implementation Outcome
구현 완료 상태에서는 (1) AI Office가 backend-neutral public execution contract만 사용하고, (2) action/provider observability source-of-truth가 분리된 채 소비 가능하며, (3) Full Plan 최종 assignment/Router 선택/MPRF runtime/Full MCP effect authority가 보존되고, (4) state-changing authority가 일시적으로 불가해도 read-only 진행과 typed wait/manual-action handoff가 가능하며, (5) Office Project Factory/Daily Loop/AOH-004 regression을 통과한 완전한 exit evidence만 `AI_OFFICE_STABLE_BASELINE` closure 후보를 생성할 수 있다.

## Relevant Runtime Flow
1. Full Plan establishes task/capability intent and assignment authority.
2. Model execution uses the Router request/decision envelope; AI Office must never supply a provider/model choice.
3. Provider runtime is owned by MPRF and emits provider-runtime events.
4. State-changing action handoff is governed by Execution Backend contracts/adapters and Full MCP owns action/effect truth.
5. If the action route is unavailable, existing bounded Manual Action can be authorized; read-only capability does not inherit mutation authority.
6. Full MCP and MPRF already emit separate event domains with shared correlation identifiers; PHASE 5 must add a consumer boundary rather than merge them.

# EC-03 ARCHITECTURE / COMPONENTS / CHANGE TARGETS

## Source Projection ID-06 — Architecture Design

## Current Architecture Boundary
The design boundary begins above the existing Full Plan/Router/MPRF/Execution Backend/Full MCP stack. Those owners remain canonical. AI Office is added as a new operating/governance layer that consumes public contracts and stores only office-domain state plus immutable references to external authority artifacts.

## Target Architecture
```text
USER
  ↓
AI Office Governance / Office Lifecycle / Workflow State
  ├─ Requirement Intake → Context Assembly → Full Plan handoff
  ├─ System Capability Owner Routing → Full Plan / Router / MPRF / Execution Backend owners
  ├─ Agent/Capability Eligibility + Foundry + Activation Governance
  ├─ Execution Coordinator → public Execution Backend boundary → Full MCP action/effect authority
  ├─ Observability Consumer ← Action-runtime public projection
  │                         ← Provider-runtime public projection
  ├─ Recovery Coordinator → owning recovery/action boundaries + same Gate
  └─ Office KPI/Status/Report read models

Full Plan: planning/decomposition/final assignment
Multi-Provider Router: provider/model selection
MPRF: provider runtime
Full MCP: action/effect/reconciliation truth
```

## Preserved Architecture
- Existing Router request/decision authority and canonical envelope.
- Existing MPRF provider runtime, registry/lifecycle/failure/checkpoint semantics.
- Existing Full MCP action/effect/authorization/reconciliation semantics.
- Existing Execution Backend Contract and Manual Action semantics.
- Full Plan Gate/fan-in/final-assignment semantics.

## Changed Architecture
- Add additive orchestration public boundaries for AI Office execution and observability.
- Add `runtime/ai_office` domain with office state/governance/foundry/recovery/reporting coordination.
- Add new AI Office validation/E2E/negative-space tests.

## New Architecture Elements
- AI Office versioned contracts and durable office state.
- Public execution facade + adapter.
- Public dual-domain observability facade.
- Capability/agent governance projection.
- Foundry/Office Project Factory.
- Risk/permission/activation governance.
- Recovery/reporting projections.
- Integrated qualification and closure candidate validator.

## Architecture Decisions
| ID | Decision | Related Requirements | Rationale |
|---|---|---|---|
| ARC-001 | Authority-preserving overlay: AI Office is operating/governance layer, not alternate planner/router/runtime/backend. | REQ-003/005/020/021, SEC-006 | Prevents canonical authority duplication. |

## Component Details

### CMP-004 — Execution Backend Contract Boundary
Responsibility: Preserve the verified `runtime/orchestrator/production_execution_gateway.py` backend-neutral `ExecutionRuntimeHandler` injection point as the exact AOH-001 downstream port. The new office adapter validates/translates public office DTOs and invokes only the injected handler.  
Inputs: `OfficeExecutionRequestV1`, validated execution/authorization bindings, injected `ExecutionRuntimeHandler`.  
Outputs: backend-neutral execution response projected to `OfficeExecutionResultV1`.  
Dependencies: existing Execution Backend Contract/public execution semantics; concrete runtime composition remains external.  
State Behavior: translation/validation only; no direct action/effect state ownership.  
Error Behavior: missing/invalid handler, binding mismatch, backend-specific field leakage or unsupported semantics -> typed BLOCKED/contract error.  
Compatibility: if implementation-start source revalidation shows the verified port changed without material WHAT drift, use the exact semantics-preserving public equivalent and record the source-binding change; material authority drift triggers `SOURCE_DRIFT_DETECTED`.  
Preserved Behavior: no `runtime.full_mcp` import, no direct `FullMCPBackendAdapter` construction/selection, no provider/model selection in AI Office or the office adapter.

### CMP-005 — AI Office/Public Contracts
Responsibility: Define frozen/versioned DTOs, safe IDs, canonical JSON/digest rules, source refs and forbidden-field constraints.  
Inputs: approved requirement/identity/auth/observation references.  
Outputs: validated immutable DTOs.  
Dependencies: standard library; orchestration public contracts only.  
State Behavior: pure validation; no effects.  
Error Behavior: malformed/unknown version/binding mismatch fails closed.  
Compatibility: versioned V1 schemas; additive future versions require explicit compatibility.  
Preserved Behavior: no provider/model/backend internals exposed.

### CMP-006 — AI Office Durable State Store
Responsibility: Persist AI Office-owned state under `_workspace/ai-office/<project_run_id>/` using append-only transition journal plus atomic snapshot, file lock, canonical digest and monotonic revision.  
Inputs: validated domain state transition.  
Outputs: `OfficeStateSnapshotV1` + transition refs.  
Dependencies: CMP-005.  
State Behavior: create-once run identity, append-only transitions, atomic snapshot replace.  
Error Behavior: digest-chain/revision/identity mismatch blocks load/append.  
Compatibility: no database dependency; external authority data stored only as refs/digests.  
Preserved Behavior: Full MCP/MPRF stores remain separate.

### CMP-007 — Requirement Intake & Context Assembly
Responsibility: Bind approved requirement refs and assemble deterministic context using explicit source precedence: current user decision > approved plan > verified repository/baseline > verified run/workflow/foundry state > explicit technical assumptions.  
Inputs: source refs/digests.  
Outputs: `RequirementEnvelopeV1`, `ContextAssemblyV1`.  
Dependencies: CMP-005/006 and existing validated context/source mechanisms.  
State Behavior: cache by input digest only; no semantic source rewriting.  
Error Behavior: stale/missing/higher-precedence conflict -> blocked/source-drift disposition.  
Compatibility: Full Plan receives context but remains planning authority.

### CMP-008 — Office Registry & Workflow Coordinator
Responsibility: Manage office/department definitions, schedules, run state and workflow state; record Full Plan outputs as external refs.  
Inputs: requirement/context, governance refs, external task/assignment refs.  
Outputs: OfficeRun/Workflow state transitions.  
State Behavior: controlled state machine with WAITING_APPROVAL, WAITING_STATE_CHANGE_AUTHORITY and RECOVERY_COORDINATION branches.  
Error Behavior: illegal transitions rejected.  
Preserved Behavior: no task decomposition, final assignment or fan-in decision.

### CMP-009 — Capability/Agent Governance
Responsibility: Map capability need to owning system boundary; expose Find Agent/candidate eligibility; wrap existing source/adoption mechanisms.  
Inputs: required capabilities, execution authority, registry/inventory/provenance refs.  
Outputs: owner-boundary dispatch + candidate set.  
State Behavior: candidate status is versioned and approval-bound.  
Error Behavior: unknown owner/source/version/permission -> blocked.  
Preserved Behavior: Router selects provider/model; Full Plan assigns agent; MPRF remains provider runtime.

### CMP-010 — AI Office Foundry
Responsibility: Create versioned Office Project Definition, Operating Contract, lifecycle and declarative scaffold intent.  
Inputs: approved project definition/template/governance refs.  
Outputs: `OfficeOperatingContractV1`, `ScaffoldIntentV1`.  
State Behavior: DRAFT→GOVERNED→SCAFFOLD_PENDING→SCAFFOLD_VERIFIED→PILOT/PRODUCTION gates.  
Error Behavior: no direct effect when execution/approval refs absent.  
Preserved Behavior: all mutations use CMP-012.

### CMP-011 — Approval/Risk/Permission Governance
Responsibility: Evaluate scope/risk/permission and human approval freshness, then emit durable governance decisions.  
Inputs: requested action/capability scope, requirement refs, user approval record.  
Outputs: `RiskEnvelopeV1`, `GovernanceDecisionV1`, `ActivationGateV1`.  
State Behavior: fail-closed dual gate.  
Error Behavior: stale/missing approval, scope expansion or permission mismatch -> BLOCKED.  
Preserved Behavior: does not replace Full MCP authorization validation.

### CMP-012 — AI Office Execution Coordinator
Responsibility: Convert governed action/scaffold intent to public Execution Backend request and store result/manual-action refs.  
Inputs: intent + governance decision + execution contract/package refs.  
Outputs: OfficeExecutionRequest/Result refs and workflow transition.  
State Behavior: READY→EXECUTION_PENDING→COMPLETED/BLOCKED/FAILED or WAITING_STATE_CHANGE_AUTHORITY.  
Error Behavior: typed blocked state, no silent fallback.  
Preserved Behavior: no direct Full MCP import/effect handling/provider selection.

### CMP-013 — Observability Consumer
Responsibility: Correlate action/provider source projections into a read model.  
Inputs: ActionRuntimeObservationRefV1 and ProviderRuntimeObservationRefV1.  
Outputs: CorrelatedObservationV1.  
State Behavior: append office observation refs only; sources immutable.  
Error Behavior: correlation/source digest mismatch rejects.  
Preserved Behavior: distinct source domains remain canonical.

### CMP-014 — Recovery Coordinator
Responsibility: Track escalation/remediation/validation/review/same-gate refs.  
Inputs: failure/observation/workflow/approval refs.  
Outputs: RecoveryCoordinationV1 and workflow state.  
Preserved Behavior: no provider recovery policy, action replay or Gate decision.

### CMP-015 — Reporting Aggregator
Responsibility: Produce office KPI/status/report read models.  
Inputs: office snapshots, workflow/observation/recovery refs.  
Outputs: OfficeReportV1.  
Preserved Behavior: no task fan-in/completion/action truth.

### CMP-016 — Qualification & Closure
Responsibility: Define E2E/regression/security/traceability qualification and baseline closure candidate/evidence equality rules.  
Inputs: all validation/evidence refs.  
Outputs: qualification report structure and BaselineClosureCandidateV1.  
Preserved Behavior: does not itself run tests or declare baseline in design phase.

## Interface Details

### IF-001 — RequirementEnvelopeV1
Input: `requirement_id`, `source_ref`, `source_digest`, `planning_authority_ref`, `constraints_refs`, `correlation_id`.  
Output: canonical immutable envelope + `envelope_digest`.  
Contract: source digest and approved requirement ID must match authority register; free-form normalization cannot alter acceptance semantics.  
Error Handling: unknown ID/digest mismatch -> `SOURCE_BINDING_BLOCKED`.  
Security: no secrets/provider/model data.

### IF-002 — OfficeRun / Workflow State API
Input: `office_id`, `department_id`, `run_id`, `workflow_item_id`, current state/version, requested transition, schedule ref, external Full Plan assignment/fan-in refs when present.  
Output: immutable `OfficeRegistryV1`, `OfficeRunV1` and `WorkflowItemV1` projections plus next version and transition digest.  
Contract: compare-and-advance semantics require the supplied current version/digest; only ID-09 declared transitions are valid. Assignment/fan-in values are external authority references and cannot be synthesized or altered by this API.  
Error Handling: stale version, undeclared transition, identity mismatch, or attempted assignment/completion authority mutation -> BLOCKED.  
Ownership: AI Office office/workflow lifecycle state only; Full Plan retains task decomposition, final assignment, fan-in and completion authority.

### IF-003 — ContextAssemblyV1
Input: repository identity ref, baseline ref, requirement refs, run/workflow/foundry refs, explicit assumption refs.  
Output: ordered context item refs + source-precedence version + digest.  
Contract: precedence is explicit and deterministic; content is references/digests where possible.  
Error Handling: conflicting higher authority/stale source -> block.  
Compatibility: Full Plan consumes context without transferring planning authority.

### IF-004 — CapabilityNeedV1
Input: `capability_need_id`, `required_capabilities[]`, `execution_authority`, `purpose_ref`, `scope_ref`.  
Output: owner boundary enum `{FULL_PLAN, MULTI_PROVIDER_ROUTER, MPRF, EXECUTION_BACKEND, AI_OFFICE}` or typed block; no provider/model identity.  
Security: provider/model fields are forbidden.

### IF-005 — AgentCandidateSetV1
Input: `CapabilityNeedV1`, governed capability/agent inventory refs and digests, approved source/version/permission/risk eligibility facts.  
Output: ordered-by-stable-identity candidate records containing agent/capability identity, version, capability match, permission/risk eligibility disposition and evidence refs; no provider/model identity and no selected/final assignee field.  
Contract: candidates are eligibility/context only. Candidate inclusion requires current governed inventory evidence; absence or ambiguity yields an empty/blocked candidate disposition rather than inferred eligibility.  
Error Handling: stale inventory, unapproved source/version, permission mismatch, duplicate identity, or provider/model/final-assignment field -> BLOCKED.  
Ownership: AI Office candidate governance only; Full Plan alone performs final task-to-agent assignment.

### IF-006 — OfficeExecutionRequestV1
Input: project/run/workflow/task refs, operation intent ref, `expected_effect_semantics`, governance/risk/delegated-auth/binding refs, execution package/contract refs, correlation ID.  
Output: canonical request digest.  
Contract: state-changing request requires governance and authorization lineage; the orchestration-side adapter accepts an injected backend-neutral `ExecutionRuntimeHandler` and never imports/selects/constructs the concrete Full MCP backend. The public boundary contains no Full MCP internal paths/classes and no provider/model fields.  
Error Handling: missing lineage, stale source, effect mismatch, absent/nonconforming runtime handler or backend-specific leakage -> BLOCKED.

### IF-007 — OfficeExecutionResultV1
Input: public execution result from adapter.  
Output: status `{COMPLETED,BLOCKED,FAILED,PENDING}`, result/effect/audit/reconciliation refs.  
Contract: identity/correlation request binding exact.  
Security: no raw stdout/stderr/secrets/internal object handles.

### IF-017 — Mutation-Unavailable Handoff / Non-Mutating Continuation
Input: blocked state-changing execution disposition, capability/execution-authority need, dependency-safety result, existing Manual Action package/authorization ref when present, external Full Plan/Router handoff ref for non-mutating continuation.  
Output: `ManualActionHandoffRefV1` or `NonMutatingContinuationRefV1`, each identity/correlation/digest bound.  
Contract: both DTOs are defined in `runtime/orchestrator/office_execution_contract.py` before the AI Office coordinator is created. The continuation DTO contains required capabilities and `READ_ONLY` execution authority but forbids provider/model fields; the manual-action DTO references existing bounded authorization/package evidence and never embeds mutation authority itself.  
Error Handling: mixed read-only/state-changing capability, missing dependency-safety binding, stale Manual Action authorization, or provider/model field -> BLOCKED.  
Ownership: this interface records disposition/handoff only; Full Plan/Router select execution route and existing Manual Action owns bounded manual mutation.

### IF-008 / IF-009 — Observation Source Refs
Input: source-owned event/result record.  
Output: `source_domain`, `source_ref`, `event_digest`, `correlation_id`, `operation_request_id`, `task_execution_id`, `sequence`, bounded status/fact projection.  
Contract: source adapter validates source schema/digest before projection; projection never becomes source-domain canonical event.  
Error Handling: malformed source or digest mismatch -> observation blocked.

### IF-010 — CorrelatedObservationV1
Input: validated `ActionRuntimeObservationRefV1` and/or `ProviderRuntimeObservationRefV1` sharing bound project/run/task-execution/correlation identity.  
Output: correlation view containing source-ref sets, correlation identity, bounded status summary and a deterministic correlation digest.  
Contract: at least one validated source ref is required; each source retains its original `source_domain`, `source_ref`, sequence and digest. The correlation view never rewrites either source as canonical truth and cannot manufacture missing action/provider facts.  
Error Handling: identity/correlation mismatch, duplicate conflicting source ref, digest failure, or attempted cross-domain truth synthesis -> BLOCKED.  
Ownership: consumer/read-model correlation only; Full MCP and MPRF remain independent sources of truth.

### IF-011 — GovernanceDecisionV1
Input: risk envelope, permission set, human approval ref/digest/freshness, scope binding.  
Output: `decision={ALLOW,BLOCK,APPROVAL_REQUIRED}`, activation scope, decision digest.  
Security: cannot infer permission from necessity; no approval synthesis.

### IF-012 — OfficeProjectDefinitionV1
Input: office/project identity, approved requirement/context refs, approved template refs/digests, operating policy refs, lifecycle version and intended project-root binding.  
Output: immutable project definition containing identity, operating-contract ref/digest, template/source refs, lifecycle initial state, allowed scaffold scope and definition digest.  
Contract: definition is declarative and effect-free; target root must remain within the approved project/Foundry scope and no sibling replacement root, deployment or publication intent is implied.  
Error Handling: unapproved template/source, identity/root conflict, lifecycle-version mismatch, or effect-bearing field -> BLOCKED.  
Ownership: Foundry definition/lifecycle contract only; filesystem/Git effects require IF-013→IF-006 governed execution.

### IF-013 — ScaffoldIntentV1
Input: project definition, approved templates, intended path set, expected changes, validation refs.  
Output: declarative scaffold effect intent and scope digest.  
Contract: direct I/O methods are absent; execution occurs only through IF-006.

### IF-014 — RecoveryCoordinationV1
Input: failure class/source ref, affected workflow refs, approval state, remediation/focused-test/regression/review/same-gate refs.  
Output: recoverable coordination state.  
Contract: recovery stage advancement requires preceding refs; bypass prohibited.

### IF-015 — OfficeReportV1
Input: immutable AI Office state/observation/recovery refs.  
Output: office KPI/status/report plus source refs.  
Contract: report is a read model; no task completion/fan-in mutations.

### IF-016 — BaselineClosureCandidateV1
Input: complete required evidence IDs/digests and canonical identity.  
Output: closure candidate digest + alias equality disposition.  
Contract: exact required evidence set, Blocker=0, unresolved Major=0, traceability=100%, canonical/alias evidence equality.  
Error Handling: partial/mismatched evidence -> NO_GO candidate only.

## Source Projection ID-09 — Data / Control / State Flow

## Data Flow
1. Approved requirement/source reference enters IF-001; no requirement text is silently changed.
2. Context Assembly binds repository/baseline/run/workflow/foundry inputs and emits a deterministic context digest.
3. Office workflow hands context to Full Plan and stores only returned planning/task/assignment references.
4. Capability governance classifies required capabilities and owner boundary; candidate agent eligibility may be attached, but final assignment remains external.
5. Governance produces risk/permission/human-approval decision for any activation/state-changing path.
6. Foundry/workflow emits declarative action or scaffold intent.
7. Execution Coordinator converts the governed intent to IF-006; orchestration adapter hands it to the approved Execution Backend/Full MCP path.
8. Execution result is stored as a reference, while action-runtime and provider-runtime source events remain in their own domains.
9. Observability Consumer correlates source refs; Recovery Coordinator reacts to typed failures without executing recovery effects itself.
10. Reporting creates office-level read models. Qualification consumes test/evidence refs; closure candidate is built only from complete exit evidence.

## Control Flow
1. `TASK-001/GATE-001` source/entry revalidation.
2. AOH-001 (TASK-002~004) and AOH-003 (TASK-005) proceed in parallel-safe ownership areas.
3. `FI-001` requires GATE-002 and GATE-003 before AOH-002 core starts.
4. AOH-002 core contracts/state/context/workflow/governance establish base; capability/onboarding/foundry/recovery/reporting build on them with bounded parallelism.
5. Representative E2Es and security negative-space definitions fan in to AOH-004 qualification.
6. Only GATE-005 GO permits the execution-stage closure process to declare `AI_OFFICE_STABLE_BASELINE`.

|---|---|---|---|

# EC-12 RECOVERY

## Source Projection ID-19 — Recovery Design

## RCV-001 — Source Drift / Entry Failure
Trigger: root/HEAD/worktree/roadmap/predecessor authority materially differs from approved baseline.  
Affected Tasks: TASK-001 and all downstream tasks.  
Recovery Flow: Failure → Diagnose drift → Reverify authoritative source → determine HOW-only vs WHAT impact → focused source validation → independent review → GATE-001 re-evaluation.  
Recovery Validation: TEST-001.  
Recovery Gate: GATE-001.  
Prohibited Bypass: treating drift as accepted, silently changing root/version/scope; WHAT impact requires PLAN_REVISION_REQUIRED.

## RCV-002 — Execution Integration / State-Change Authority Unavailable
Trigger: state-changing route is ineligible or execution adapter returns typed blocked state.  
Affected Tasks: TASK-003/004 and workflows requiring mutation.  
Recovery Flow: Failure → Diagnose condition → continue dependency-safe read-only work → either approved bounded Manual Action or wait for separately authorized state-changing capability → focused validation → regression → independent review → same Gate re-evaluation.  
Recovery Validation: TEST-005/006/023.  
Recovery Gate: GATE-002 or owning workflow Gate.  
Prohibited Bypass: mutation via read-only capability, provider hardcoding, automatic authority substitution.

## RCV-003 — Approval / Permission / Onboarding Failure
Trigger: stale/missing approval, permission mismatch, unapproved source/version/risk state.  
Affected Tasks: TASK-010/012 and dependents.  
Recovery Flow: Failure → Diagnose exact binding → remediate source/risk/permission/approval record under approved scope → focused validation → regression → independent review → GATE-004 re-evaluation.  
Recovery Validation: TEST-017~022.  
Recovery Gate: GATE-004.  
Prohibited Bypass: synthesized approval, permission expansion, unauthorized activation.

## RCV-004 — Observability Correlation / Source Integrity Failure
Trigger: event digest/source domain/correlation mismatch.  
Affected Tasks: TASK-005/013/014.  
Recovery Flow: Failure → Diagnose owning source adapter → correct projection only → focused validation → dual-domain regression → independent review → same Gate re-evaluation.  
Recovery Validation: TEST-007~009/024/025.  
Recovery Gate: GATE-003 or GATE-004.  
Prohibited Bypass: rewriting source event, merging domains, using reporting data as canonical action/provider truth.

## RCV-005 — AOH-004 Regression / Closure Failure
Trigger: E2E/regression/negative-space/traceability/evidence equality fails.  
Affected Tasks: TASK-015~017.  
Recovery Flow: Failure → Diagnose finding → remediate approved HOW only → focused validation → targeted/full regression as blast radius requires → independent EDP review → GATE-005 re-evaluation.  
Recovery Validation: TEST-026~032.  
Recovery Gate: GATE-005.  
Prohibited Bypass: baseline declaration with missing evidence, unresolved Major/Blocker, partial alias, or plan-boundary change.

- 테스트 문자열을 느슨하게 만들거나 한 환경만 검사하지 않는다.
- 제품 선택 정책을 테스트 통과만을 위해 바꾸지 않는다.

### 4.2 CMP-R02 — Canonical Plan Binding & Registry Isolation (D2)

**변경 대상**

| 경로 | 상태 | 처리 |
|---|---|---|
| `runtime/orchestrator/project_onboarding.py` | VERIFIED_BY_DIAGNOSIS | 변경 후보 |

**canonical plan 선택 규칙**

1. 기존 등록 항목에 `canonical_plan`이 있으면 그 경로만 canonical authority로 검증한다.
2. 경로가 허용 project root 내부인지, 일반 파일인지, 정책상 허용된 이름/위치인지, 등록 digest와 일치하는지 검증한다.
3. 같은 프로젝트에 다른 계획 문서가 존재해도 등록 binding을 자동 변경하지 않는다.
4. 신규 등록 또는 canonical binding이 없는 항목만 후보 탐색을 사용한다.
5. 신규 후보가 둘 이상이면 기존처럼 fail closed 한다.
6. 승인 증거 없이 파일 삭제·이름 변경·자동 선택을 하지 않는다.

**조회 격리 규칙**

- `inspect(project_id)`는 요청 대상의 검증 결과만 반환하거나 그 대상 오류를 낸다.
- `entries()`는 전역 식별 무결성(alias/project 중복 등)을 먼저 검사한 뒤, 개별 항목 결과를 `VALID` 또는 `INVALID(reason)`로 수집한다.
- 개별 계획 누락·digest mismatch·경로 오류는 해당 항목을 실행 불가로 만들되 다른 정상 항목의 읽기 조회 결과를 제거하지 않는다.
- 전체 감사 API는 모든 오류를 집계하고 전체 건강 상태를 FAIL로 유지한다.
- 실행/활성화 경로는 대상 항목이 `VALID`가 아니면 계속 차단한다.

**등록 binding 보존**

- `IMPLEMENTATION_PLAN.md`와 `docs/DEVELOPMENT_PLAN.txt`를 삭제·덮어쓰기하지 않는다.
- 진단에서 확인한 두 SHA는 재현 증거이며, 현재 SHA는 구현 시작 시 다시 계산한다.

### 4.3 CMP-R03 — Continuation Dispatch/Completion Guard (D3)

**변경 대상**

| 경로 | 상태 | 처리 |
|---|---|---|
| `runtime/orchestrator/production_full_plan_runner.py` | VERIFIED_BY_DIAGNOSIS | 공통 dispatch/completion guard 후보 |
| `runtime/orchestrator/production_full_plan_boot.py` | VERIFIED_BY_DIAGNOSIS | 진입 일관성 후보 |
| `runtime/orchestrator/production_full_plan_entry.py` | PATH_TO_VERIFY | TASK-R01 call graph 후 변경 여부 확정 |
| receipt 검증 및 task/gate binding 지점 | PATH_TO_VERIFY | 기존 공개 validator 우선 재사용 |

**공통 인터페이스**

`ContinuationDecision evaluate_continuation_boundary(context, boundary)`

필수 입력:

- project_id, run_id, task_id, gate_id
- continuation contract/version
- cycle_id, generation, phase
- approved plan/spec/source/environment digests
- expected receipt kind 및 실제 receipt reference
- boundary: `PRE_DISPATCH` 또는 `PRE_COMPLETE`

결과:

- `ALLOW_VALIDATION_ONLY`
- `ALLOW_EFFECT_ONCE`
- `ALLOW_COMPLETE`
- `WAIT_EVIDENCE`
- `BLOCK(reason_code)`

이 인터페이스는 Provider/model을 선택하지 않고 기존 실행 경로로 전달 가능한지 여부만 판정한다.

**상태별 허용 행위**

| Phase | PRE_DISPATCH | PRE_COMPLETE |
|---|---|---|
| 계약/checkpoint 없음·손상 | BLOCK | BLOCK |
| RED_ARMED | 지정 RED 검증만 허용 | BLOCK |
| RED_RUNNING | 동일 RED 결과 정산만 허용; 새 effect 금지 | BLOCK |
| GREEN_READY | approval/source/environment 재검증 후 effect 1회 허용 | BLOCK |
| GREEN_RUNNING | 새 effect 금지; receipt reconciliation만 허용 | BLOCK |
| FOCUSED_VALIDATION | 지정 집중검증만 허용 | 해당 검증 PASS 전 BLOCK |
| REGRESSION_VALIDATION | 승인된 회귀검증만 허용 | 전체 요구 검증 PASS 전 BLOCK |
| BLOCKED | dispatch 0회 | BLOCK |
| COMPLETED | effect 재실행 금지 | Gate 증거까지 유효할 때만 ALLOW_COMPLETE |

**영수증 검증**

- `passed=true`만으로 신뢰하지 않는다.
- receipt의 project/run/task/cycle/generation/source digest, validation target, 실행 권한, effect identity를 현재 binding과 비교한다.
- GREEN effect receipt는 Full MCP가 소유하는 실제 effect/reconciliation 근거를 참조해야 한다.
- test receipt는 실행한 command/profile/target/result 및 collection/skip/import 상태를 포함해야 한다.
- receipt 누락 또는 불일치는 `WAIT_EVIDENCE` 또는 `BLOCK`이며, 상위 완료로 환산하지 않는다.

**durable effect 실행 순서**

1. `effect_intent_id`를 `sha256(project_id | run_id | task_id | cycle_id | approved_effect_spec_digest)`로 결정적으로 생성한다.
2. effect를 호출하기 전에 CMP-R04를 사용해 `GREEN_RUNNING + effect_intent_id + receipt=null` generation을 먼저 commit한다.
3. 기존 Execution Backend Contract를 통해 Full MCP에 같은 `effect_intent_id`를 idempotency/correlation key로 전달한다.
4. Full MCP가 반환한 canonical effect reference를 durable receipt로 저장한다. 임의 로컬 성공 boolean은 effect 증거가 아니다.
5. 저장 후 동일 key로 Full MCP reconciliation 조회를 수행해 실제 effect와 receipt를 대조한다.
6. 대조 PASS 후에만 FOCUSED_VALIDATION generation으로 전이한다.
7. 재시작 시 GREEN_RUNNING이면 effect를 즉시 재호출하지 않고 같은 key의 canonical effect/receipt를 먼저 조회한다.
8. effect가 확인되면 receipt를 복구하고 검증으로 진행한다. effect 없음이 권한 소유자의 canonical 조회로 확정된 경우에만 같은 key로 재요청할 수 있다.
9. 조회 불가·결과 불명확·key 충돌이면 `EFFECT_RECONCILIATION_REQUIRED`로 차단한다.

**IF-R01 — EffectReconciliationPortV1**

AI Office/Full Plan은 Full MCP 내부를 직접 호출하지 않고 기존 Execution Backend Contract에 다음 provider-neutral port를 사용한다.

```text
submit_or_reconcile(request) -> EffectReconciliationResultV1
```

Request 필수 필드:

- project_id, run_id, task_id, cycle_id
- effect_intent_id (idempotency/correlation key)
- approved_effect_spec_digest
- authorization_binding_ref, approval_evidence_ref
- source/environment binding digests

Result 필수 필드:

- effect_intent_id, canonical_effect_id
- status: NOT_FOUND | PENDING | APPLIED | FAILED | UNKNOWN
- canonical_receipt_ref와 receipt_digest(존재할 때)
- authorization/effect/spec binding digests
- observed_at와 owning-domain evidence reference

계약 의미:

- `submit_or_reconcile`는 동일 `effect_intent_id`에 대해 Full MCP 소유 경계에서 원자적인 deduplication을 적용한다. 호출자가 `lookup → submit`을 따로 수행하는 check-then-act 경쟁을 만들지 않는다.
- 최초 유효 요청은 승인된 effect를 등록·실행하고, 동일 key 재요청은 새 effect를 만들지 않고 기존 canonical 상태를 반환한다.
- 같은 key에 다른 effect spec/authorization binding이 들어오면 `IDEMPOTENCY_BINDING_CONFLICT`로 fail closed 한다.
- `APPLIED`는 canonical receipt 검증 후에만 반환한다. `PENDING`은 재호출 시 상태 조회만 하며 새 effect를 만들지 않는다.
- `FAILED`의 재시도 가능성은 Full MCP canonical failure/reconciliation 정책이 명시한 경우에만 같은 key로 재평가한다.
- `UNKNOWN` 또는 port 접근 불가이면 `EFFECT_RECONCILIATION_REQUIRED`; 실행·완료를 차단한다.
- Port adapter는 effect truth를 새로 만들지 않고 Full MCP canonical result를 투영한다.

정확한 기존 adapter 파일과 Full MCP 지원 표면은 TASK-R01에서 `PATH_TO_VERIFY`한다. 기존 공개 adapter가 없으면 CMP-R03 소유 범위 안에서 Execution Backend Contract adapter를 추가하되 Full MCP 내부 정책·저장소를 복제하지 않는다. Full MCP 소유 경계가 원자적 동일-key deduplication과 canonical reconciliation을 제공하지 않는 것으로 확인되면 source reality가 본 설계의 필수 capability와 충돌하므로 GATE-R01 `SOURCE_DRIFT_DETECTED / NO_GO`로 반환하고 구현을 시작하지 않는다.

**중단 창별 동작**

| 중단 위치 | 재시작 동작 | effect 재호출 |
|---|---|---|
| intent commit 전 | 이전 일관 generation 유지 | 허용 안 됨; 상태 재평가 |
| intent commit 후, dispatch 전 | 동일 key로 `submit_or_reconcile` 1회 호출; owning boundary가 원자적으로 reconcile-or-submit | port 내부에서만 조건부 허용 |
| dispatch 후, 응답 전 | canonical lookup/reconciliation | 확인 전 금지 |
| 응답 후, receipt commit 전 | canonical effect에서 receipt 복구 | 금지 |
| receipt commit 후, validation 전 | receipt 재검증 후 validation 진행 | 금지 |
| validation 후, completion 전 | 완료 guard 재평가 | 금지 |

**LEGACY 호환**

- task/job에 TDD_V1 continuation 계약이 명시된 경우에만 새 guard를 강제한다.
- LEGACY 경로에는 기존 Gate/approval/permission 검사를 그대로 적용하고 새로운 phase를 추정하지 않는다.
- boot, resume, direct runner 등 모든 TDD_V1 진입 경로는 동일 guard를 호출해야 한다.

### 4.4 CMP-R04 — Generational Continuation Store (D4)

**변경 대상**

| 경로 | 상태 | 처리 |
|---|---|---|
| `runtime/orchestrator/implementation_continuation.py` | VERIFIED_BY_DIAGNOSIS | 주 변경 대상 |
| `runtime/orchestrator/durable_io.py` | VERIFIED_BY_DIAGNOSIS | 기존 안전 저장 재사용; 공용 변경은 별도 근거 필요 |
| continuation durability/fault-injection 테스트 | PATH_TO_VERIFY/PLANNED_CREATE | 기존 테스트 확인 후 최소 추가 |

**저장 레이아웃 개념**

```text
continuation/<binding-key>/
  generations/<generation-id>/checkpoint.json
  generations/<generation-id>/manifest.json
  commits/<generation-id>.json
  latest.json
```

실제 경로명은 기존 레이아웃 호환성을 확인한 뒤 정하되, generation과 manifest/pointer의 의미는 유지한다.

**generation manifest 필수 필드**

- schema_version, continuation_contract_version
- project_id, run_id, task_id, cycle_id
- generation_id, previous_generation_id
- phase, checkpoint_digest
- approval/spec/source/environment digests
- effect_intent_id, effect_receipt_ref 또는 명시적 null
- created_at, writer identity/authority metadata

**commit record 필수 필드**

- generation_id, previous_committed_generation_id
- manifest_digest, checkpoint_digest
- previous_commit_digest, commit_digest
- binding key와 schema version

commit record는 generation의 확정 표식이며 digest chain으로 이전 확정 세대와 연결한다. `latest.json`은 빠른 조회용 포인터이지 확정의 유일한 근거가 아니다.

**쓰기 프로토콜**

1. 새 generation 디렉터리에 checkpoint를 안전 저장한다.
2. checkpoint를 다시 읽고 canonical digest와 binding을 검증한다.
3. 같은 generation manifest를 안전 저장하고 다시 검증한다.
4. 이전 commit digest에 연결한 commit record를 안전 저장하고 다시 검증한다.
5. `latest.json`을 `{generation_id, commit_digest, manifest_digest, checkpoint_digest}`로 원자 교체한다.
6. latest를 다시 읽어 동일 generation을 가리키는지 확인한다.
7. 1~6이 성공한 뒤에만 다음 상태로 진행한다.

Step 4가 성공한 시점에 generation은 **COMMITTED**다. Step 5 또는 6이 실패하면 쓰기 API는 일반 실패나 미커밋으로 반환하지 않고 `COMMITTED_POINTER_STALE(generation_id, commit_digest)`를 반환한다. 호출자는 다음 generation 생성·effect 재호출·동일 generation 재작성을 금지하고, 같은 binding lock 안에서 recovery를 호출한다. Recovery는 commit chain의 유일한 tip을 검증해 `latest`만 복구하고 재검증한다. 복구 PASS 후 원래 호출은 `COMMITTED_RECOVERED`로 종료하고, 복구 불가 또는 fork이면 `CONTINUATION_RECOVERY_BLOCKED`로 차단한다.

Step 4 전 실패한 prepared checkpoint/manifest에는 commit record가 없으므로 현재 상태가 아니다. 동일 상태 전이를 다시 시도할 때 새 generation id를 사용하며, prepared artifact는 감사용으로 남기거나 별도 정리 절차가 처리한다. effect intent가 포함된 prepared artifact만으로 effect를 호출하지 않는다.

**복구 프로토콜**

1. latest가 가리키는 generation의 manifest/checkpoint를 검증한다.
2. 유효하면 그것만 현재 상태로 채택한다.
3. latest가 손상됐거나 참조가 불일치하면 `commits/`의 digest chain을 검증하고, binding이 일치하는 마지막 연속 committed generation을 찾는다.
4. commit record가 없거나 chain에서 분기·단절된 generation은 최신 timestamp라는 이유로 채택하지 않는다.
5. GREEN_RUNNING에서 effect 실행 여부가 불명확하면 이전 generation으로 조용히 되돌리지 않고 `EFFECT_RECONCILIATION_REQUIRED`로 차단한다.
6. 동일 effect_intent_id에 유효 receipt가 확인되면 effect를 재실행하지 않고 다음 검증 단계로 전이한다.
7. 복구 근거가 없으면 `CONTINUATION_RECOVERY_BLOCKED`와 필요한 수동 확인을 기록한다.

**V1 읽기 호환**

- 기존 단일 checkpoint/latest 형식을 읽는 adapter를 제공한다.
- 기존 쌍이 일관되면 generation 0의 읽기 전용 legacy snapshot으로 해석한다.
- 첫 상태 변경 시 검증된 legacy snapshot을 새 generation으로 승격한다.
- 기존 쌍이 불일치하면 자동 승격·덮어쓰기를 금지하고 복구 차단한다.
- 전환 완료 전 기존 파일을 삭제하지 않는다.

**동시성/단일 writer**

- 동일 binding-key에는 기존 durable lock/lease를 이용한 single-writer를 강제한다.
- lock/lease 만료 후 새 writer는 committed chain과 canonical effect 상태를 재조정하기 전 쓰지 않는다.
- 서로 다른 binding-key만 병렬 저장할 수 있다.
- generation 번호 충돌 또는 commit chain fork는 자동 병합하지 않고 차단한다.

**artifact 상태와 정리 규칙**

| 상태 | 판별 근거 | 현재 상태 채택 | 정리 |
|---|---|---|---|
| PREPARED | checkpoint/manifest만 있고 commit record 없음 | 금지 | 보존 후 별도 GC; 실행 경로에서 무시 |
| COMMITTED | 유효 commit record와 연속 digest chain | 허용 | 보존 |
| POINTER_STALE | committed tip과 latest 불일치 | committed tip 검증 후 latest 복구 | 복구 evidence 기록 |
| ORPHAN | chain에 연결되지 않은 generation/commit | 금지 | 자동 삭제 금지, 감사 대상으로 격리 |
| FORKED | 같은 previous commit에서 복수 commit | 금지 | 수동 진단 전 전체 binding 차단 |

## 7. Gate, 증거, 복구

### 7.0 Evidence 보관·검증 계약

- EV-R01~R18은 candidate HEAD, 생성 task, 생성 시각, 명령/환경, 대상 digest, 결과 digest를 포함한다.
- 저장 위치는 기존 Phase 5 execution evidence namespace를 재사용하며, TASK-R01에서 정확한 경로를 확인해 기록한다(`PATH_TO_VERIFY`).
- 각 Gate의 reviewer는 증거 생성 작업과 분리한다. 독립 reviewer가 없는 경우 Gate는 PASS가 아니라 대기 상태다.
- 로그에 비밀값을 포함하지 않고, 원본이 외부 저장소에 있으면 immutable reference와 digest를 남긴다.
- Runtime evidence가 생성되기 전에는 예상 증거로만 표기하며 PASS를 주장하지 않는다.

| Evidence | 생성자 | 검증자 | 주요 binding | Acceptance / Gate |
|---|---|---|---|---|
| EV-R01~03 | TASK-R01 owner | Design/Entry reviewer | plan/design/root/HEAD/runtime/run digest | drift·public contract 미해결 0 / R01 |
| EV-R04~06 | TASK-R02 owner | Validation reviewer | candidate HEAD, env manifest, profile, collection | deterministic profile·누락/skip 설명 / R02 |
| EV-R07~08 | TASK-R03 owner | Registry/security reviewer | alias/project/plan digest, target status | 정상 조회 PASS·손상 실행 BLOCK·audit FAIL / R02 |
| EV-R09~11 | TASK-R04 owner | Durability reviewer | binding key, generation, commit chain, effect intent | fault point별 단일 결정·duplicate 0 / R03 |
| EV-R12~14 | TASK-R05 owner | Execution-boundary reviewer | run/task/cycle, receipt/effect ref, phase | BLOCKED dispatch 0·valid effect ≤1·LEGACY 회귀 0 / R04 |
| EV-R15~18 | TASK-R06 owner | Independent implementation reviewer | 동일 candidate HEAD와 전체 prior evidence digest | 회귀/E2E PASS·blocker/major 0 / R05 |

### GATE-R01 — 설계/소스 진입

- GO: 승인 identity 일치, drift 해결, worktree 변경 소유권 명확.
- NO_GO: 승인 문서·root·branch/HEAD 적용 대상 불명확.

### GATE-R02 — D1/D2 기반 복구

- GO: RT-01~05 PASS, 테스트 완화 0, 손상 대상 fail closed 유지.
- NO_GO: 정상 프로젝트 조회가 여전히 타 항목 오류로 실패하거나 invalid 대상 실행 가능.

### GATE-R03 — D4 내구성

- GO: RT-10~12 PASS, duplicate effect 0, 불명확 effect 차단.
- NO_GO: timestamp/orphan 자동 채택, 무한 re-arm, receipt 없는 재실행.

### GATE-R04 — D3 실행 연결

- GO: RT-06~09 PASS, 모든 TDD_V1 진입 경로 동일 guard 사용, LEGACY 회귀 0.
- NO_GO: BLOCKED dispatch 또는 TDD 미완료 COMPLETED가 1건이라도 존재.

### GATE-R05 — 통합 자격

- GO: 전체 회귀와 격리 E2E PASS, blocker 0, unresolved major 0, 독립 설계/구현 검토 PASS.
- CONDITIONAL_GO/NO_GO: 미확인 운영 UI·대기 run은 구현 자격과 구분하되 운영 복구 선언은 금지.

주의: 본 문서에 대한 `implementation-design-diagnosis`는 구현 전 승인 준비 절차이며 GATE-R01보다 앞선다. GATE-R05의 독립 검토는 구현 결과와 runtime evidence에 대한 별도 구현 검토다. 두 검토는 서로 대체하지 않는다.

### 복구 루프

```text
Failure → 원인 진단 → 소유 TASK로 반환 → 최소 보정
→ 집중 검증 → 회귀 → 독립 검토 → 같은 Gate 재평가
```

실패를 다음 task의 변경으로 덮지 않는다. Gate evidence에는 candidate HEAD, 명령, 환경, 결과 원본, collection/skip/import 상태, 관련 receipt digest를 포함한다.

## 8. 보안·권한·운영 경계

- 소스 변경은 승인된 개발 worktree에만 허용한다.
- 운영 Registry 데이터의 임의 수정, 대기 run 취소/재등록, 영수증 작성은 본 설계 실행 범위가 아니다.
- 실제 effect는 격리 검증에서 mock/fake로 대체하며 운영 Full MCP를 호출하지 않는다.
- push/PR/merge/배포/재시작/서비스 활성화에는 별도 실행·운영 승인이 필요하다.
- 사용자나 다른 작업의 미커밋 변경을 덮어쓰지 않는다.
- 비밀키·토큰을 evidence에 포함하지 않는다.
- Provider/model 고정, fallback 순서, quota 우회 로직을 코드나 설계에 추가하지 않는다.

## 10. 구현·운영 단계 구분과 다음 승인 지점

### 단계 A — 설계 확정

현재 문서는 Recovery Amendment DRAFT다. 독립 `implementation-design-diagnosis`에서 계획 보존, D1.4 합성 규칙, 누락, 충돌, 구현 가능성, traceability를 진단해야 한다. PASS 후 사용자는 Amendment를 승인할 수 있다. 표준 최종 파일 `AI-OFFICE-HARNESS-PH5_APPROVED_IMPLEMENTATION_DESIGN.md`는 승인된 D1.4 원본과 승인된 Amendment를 누락 없이 합성·재진단한 경우에만 교체할 수 있다.
